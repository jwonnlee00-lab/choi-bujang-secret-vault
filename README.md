# BYTE BACK 방어전 시작 틀 R5

이 저장소는 1단계에서 학생 본인이 GitHub 저장소와 Vercel 배포를 만드는 출발점입니다. 포함된 메모 네 건은 가상 자료입니다. 실제 학생 자료, 토큰, 비밀키를 넣지 마세요.

## 학생이 하는 일: 세 걸음

1. GitHub 계정을 만듭니다.
2. 방어전 1단계 카드의 **Deploy** 버튼을 누릅니다. Vercel에 GitHub로 로그인하고, 새 저장소가 **본인 계정의 Public 저장소**인지 확인한 뒤 Deploy를 누릅니다.
3. 배포가 끝나면 화면에 나온 `https://…vercel.app` 주소를 방어전 1단계 카드에 붙여넣고 제출합니다. 저장소 주소나 설정 파일은 적지 않습니다.

배포가 끝나면 `/`에서 점령된 가상 자료실을 볼 수 있습니다. `/data.json`에는 같은 가상 메모가 공개됩니다. 이 공개 상태를 확인하는 것이 1단계의 출발점입니다. 1단계 접수와 심판 판정은 포털에서 확인합니다.

## 시작 틀의 자동 처리

`vercel.json`은 정적 결과물 `public`을 배포합니다. 빌드 명령 `npm run build`는 Vercel이 제공하는 GitHub 저장소 소유자·이름, 커밋 SHA, 배포 URL을 검증하고 `public/aleph.json`을 생성합니다. 이 값이 없으면 빌드가 실패하므로, 성공한 것처럼 빈 주소를 내보내지 않습니다. `aleph.json`의 내용만으로 저장소 소유권이나 방어 성공을 인정하지 않습니다. 심판이 공개 저장소의 실제 커밋과 배포된 자료를 따로 대조해야 합니다.

`aleph.config.json`의 `repoUrl`과 `publicAppUrl`은 이전 제출 묶음 방식의 자리표시자입니다. 1단계에서는 학생이 편집하지 않습니다. 2단계 이후 코딩 도구가 필요한 설정과 보호 기능을 단계별로 작성합니다. `npm run bundle`과 `bundle-notes.json`도 1단계의 세 걸음에는 포함되지 않습니다.

로컬에서 가상 화면만 확인할 때는 `npm run build -- --local`을 사용합니다. 로컬 실행은 Vercel 배포나 심판 접수를 증명하지 않습니다. 저장소의 `src/attack-check.mjs`는 실제 배포가 된 뒤 `/data.json`을 비로그인으로 요청해 공개 가상 메모의 확인 표시를 읽습니다.

## 다음 단계의 코딩 도구에 전달할 규칙

[AGENTS.md](AGENTS.md)를 먼저 읽히고 한 번에 한 제작 단위만 요청하세요. 2단계부터는 자료 보호를 구현할 때 `public/data.json`을 복사하는 1단계 빌드 흐름도 함께 바꿔야 합니다. 3단계 이후의 로그인, 허용 경로, 5단계의 원본 API 주소, 6단계 이후 정책 규칙은 해당 단계 원고와 계약에 맞춰 추가합니다. 비밀번호·토큰·서버 전용 키·실제 학생 기록을 코드, Git, 제출 묶음에 넣지 않습니다.

`src/decider.mjs`와 `src/detect.mjs`의 로컬 시험은 반 엔진이나 운영 심판의 결과가 아닙니다. 1단계 이후 제출 묶음 계약 `aleph.defense.submission.v2`는 `scripts/bundle.mjs`에 남아 있으며, 코딩 도구가 해당 단계의 최신 배포 주소와 Git 원격을 맞춘 뒤 사용합니다.


## 2단계 제작 2 — 서버 함수로 자료 읽기

화면은 더 이상 `/data.json`에서 메모를 읽지 않고 Vercel 서버 함수 `/api/notes`를 호출합니다. 서버 함수는 `SUPABASE_URL`과 서버 전용 `SUPABASE_SECRET_KEY`를 Vercel 환경변수에서만 읽어 Supabase의 `notes` 테이블을 조회합니다. 키는 브라우저 파일, API 응답, 로그에 포함하지 않습니다.

현재 약점: `/api/notes` 자체는 아직 인증 없이 호출 가능한 공개 주소입니다. 즉 메모는 정적 파일에서 제거되었지만, 서버 함수 접근 통제는 다음 단계에서 추가해야 합니다.


## 2단계 제작 3 — 현재 공개 흔적 확인

현재 배포와 GitHub 최신 파일에서 가상 메모 문장이 남아 있는지 각각 확인합니다. 확인 대상 문자열은 예를 들어 `실습용 가상 과제 기록`, `실습용 가상 포트폴리오 기록`, `실습용 가상 리추얼 기록`, `실습용 가상 행정 기록`입니다.

### GitHub 최신 파일 확인

저장소 최신 상태에서 위 가상 메모 문장을 검색합니다. 현재 최신 파일에서 검색 결과가 없어야 합니다. 단, 이전 공개 커밋에 같은 문장이 남아 있다면 과거 공개 이력이 사라진 것은 아닙니다.

### 현재 배포 확인

현재 Production 배포의 정적 경로 `/data.json`을 열어 메모가 비어 있는지 확인하고, 현재 배포 파일에서도 위 가상 메모 문장을 찾지 못해야 합니다. 다만 과거 Deployment URL이 여전히 접근 가능하거나 캐시·이전 배포가 남아 있다면 과거 노출이 해소됐다고 기록하지 않습니다.

### 남아 있는 공개 API 약점

현재 `/api/notes`는 인증 없이 호출 가능한 공개 주소입니다. 정적 파일에서는 메모를 제거했지만, 이 API를 직접 호출하면 가상 메모 네 건이 반환됩니다. 따라서 현재 단계의 남은 약점은 “정적 파일 노출은 제거했지만 서버 함수 자체의 접근 통제는 아직 없다”입니다.

### 확인 결과 기록

- GitHub 최신 파일 검색 결과: 가상 메모 문장 없음
- 현재 Production 정적 파일 검색 결과: 가상 메모 문장 없음, `/data.json`은 빈 notes 배열
- 공개 API 잔여 약점: `/api/notes`는 아직 인증 없이 접근 가능
- 과거 노출 판단: 옛 공개 커밋 또는 옛 배포가 남아 있는 동안에는 “과거 노출이 해소됐다”고 쓰지 않음


## 3단계 저장점 — 로그인과 메모 관리

- 공개 자료실 화면에서 Supabase Auth 이메일·비밀번호 로그인 및 로그아웃을 사용합니다.
- 브라우저는 Supabase SDK로 받은 접근 토큰을 `Authorization: Bearer` 헤더에 담습니다.
- 서버 `api/notes.js`는 기존 `src/verify-login.mjs`를 이용해 토큰을 검사합니다. 인증하지 않은 요청은 자료 없이 HTTP 401로 거부합니다.
- 목록 GET은 검증된 로그인 사용자 ID와 `owner_id`가 같은 메모만 반환합니다. POST는 `owner_id`를 서버 확인 ID로 저장하고, 개별 GET·PUT·DELETE는 `/api/notes/:id`를 사용합니다.
- **남은 취약점:** 개별 메모 요청에서는 아직 소유자 권한을 확인하지 않습니다. 메모 ID를 아는 다른 로그인 사용자도 접근할 수 있으며, 4단계에서 보완합니다.
- 2단계의 `owner_id = NULL` 메모는 로그인 사용자 목록에 나타나지 않지만 DB에서 삭제되지 않았습니다.
- 1~2단계의 과거 공개 커밋이나 배포가 남아 있다면 과거 노출이 사라진 것은 아닙니다.

### 재확인

1. 현재 Vercel 배포 주소를 열고 실습용 A 계정으로 로그인합니다.
2. 메모 추가·목록·수정·삭제를 확인하고, 로그아웃 후 목록이 숨겨지는지 확인합니다.
3. 시크릿 창에서 로그인 없이 `/api/notes` 요청 시 HTTP 401인지 확인합니다.
4. `/data.json`은 비어 있는지, `/aleph.json`은 유지되는지 확인합니다.

`npm run bundle`은 별도의 로컬 `bundle-notes.json`과 Git origin, 깨끗한 작업 트리, 현재 배포에 대한 자기 점검을 필요로 합니다. 이 파일은 Git에 커밋하지 않습니다. 실제로 확인하지 않은 로그인 사용자별 요청 결과는 통과로 기록하지 않습니다.


## 4단계 저장점 — 로그인 사용자별 메모 소유권 보호

- 3단계 Supabase Auth 로그인·로그아웃, 메모 CRUD 기능은 유지합니다.
- `api/notes.js`의 개별 GET·PUT·DELETE는 검증된 사용자 ID와 DB의 `owner_id`가 같은 행에만 접근하도록 제한합니다. 타인 메모 ID는 `404 NOT_FOUND`로 거부합니다.
- POST의 `owner_id`는 클라이언트 요청값이 아닌 검증된 사용자 ID로 저장합니다. PUT에서 전달한 `owner_id` 변경 시도는 거부하며, 기존 행과 변경할 행의 소유자 조건을 확인합니다.
- 학습용 Supabase `public.notes`에 RLS를 적용했습니다. `anon`은 테이블 권한이 없고 `authenticated`에는 SELECT·INSERT·UPDATE·DELETE만 부여하며, 정책의 `auth.uid() = owner_id`로 자기 행만 허용합니다. 이는 Supabase SQL Editor에서 수동으로 실행·확인된 DB 설정이며 Git 저장소의 마이그레이션 파일로 관리하지 않습니다.
- 서버 함수가 사용하는 Secret Key는 RLS를 우회할 수 있으므로 API 소유자 검사도 유지합니다.
- 기존 공개 커밋과 과거 배포에 남은 노출 이력은 별개의 문제이며, 과거 노출이 해소됐다고 주장하지 않습니다.

### 재확인 방법

1. Vercel Production 배포에서 A와 B 계정으로 각각 로그인해 자기 메모 목록·추가·수정·삭제를 확인합니다.
2. 인증된 B가 A 메모 ID로 개별 GET·PUT·DELETE 요청을 보내면 모두 `404 NOT_FOUND`로 거부되고 A의 원본이 유지되어야 합니다. 이 세 항목은 수동으로 확인했습니다.
3. 무로그인 `GET /api/notes`는 `401 UNAUTHORIZED`, 정적 `/data.json`은 빈 메모 배열, `/aleph.json`은 현재 배포 식별 정보가 기대값입니다. 새 저장점 커밋 배포 뒤 다시 확인합니다.
4. Supabase SQL Editor에서 `information_schema.role_table_grants`, `has_table_privilege`, `pg_policies`를 확인합니다. 학습 SQL 변경은 GitHub 배포에 포함되지 않습니다.

`npm run bundle`은 깨끗한 로컬 Git 작업 트리, `origin`, 커밋되지 않은 로컬 `bundle-notes.json`, 현재 배포의 자기 점검을 필요로 합니다. 토큰·키·메모 본문은 제출 묶음에 넣지 않습니다.
